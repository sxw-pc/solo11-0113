# 分段传验台设计

交付方冻结 `manifest`，其 `body_hash` 确定版本。`file_entry` 属于版本；`chunk` 属于文件，保存半开字节区间。每份移动介质回执产生 `attempt`，其中 `receipt` 连接块与实际哈希；`issue` 保留缺失、损坏、错版本证据。`decision` 只引用指定冻结版本。原始回执字节保存在 `attempt.source`。

批次状态为草拟、清单冻结、接收中、可发布、拒收或证据不足。块逐项核验后才可用于暂存重组；暂存文件写完用原子更名，封验再独立计算整文件大小与哈希。`unsafe_path`、`case_collision`、`unknown_version`、`source_changed`、`output_conflict` 会阻断相应命令；回执问题保留在 `issue` 中。清单和回执重入按摘要幂等，冻结版本不能修改。

`python -m chunkproof demo` 创建本地合成 10 字节交付、三个块、回执、暂存输出和 JSON/Markdown 证明。测试覆盖路径拒绝、空文件、块边界、回执重入与回滚、损坏候选、多介质选择、介质事后篡改、输出冲突和完整发布。

介质保管子系统用 `custody_event` 记录可信、隔离与交接顺序；收件验收子系统用 `recipient`、`acknowledgement`、`acceptance` 固化条件、回执和结论。验收同时读取封验、保管链、清单版本与回执，封验通过但保管证明失效时仍不能交付。

发布编排使用 `rollout`、`rollout_wave`、`rollout_member`、`rollout_decision` 固化波次、带权重的收件范围和验收快照。各波次顺序开放；权重门槛、必达收件人及实际争议共同决定等待、完成或中止。

## 跨交付批次的块复用

新版本缺块时，操作员可通过本地复用计划明确选择是否借用已封验的旧交付块，减少移动介质拷贝。计划提供两种相互独立、由调用方选择的业务合同，对同一缺块输入可给出不同结论：

- `strict_provenance`（严格保管链）：只接纳与新交付同介质保管链、同收件范围且在新版本下有验真回执的块；不产生跨版本借用，缺块保持“仍缺块”。证据范围仅含新版本回执与当前保管链。
- `content_reuse`（内容复用）：允许跨版本借用逐字节同长同哈希的旧块补齐内容，但把旧版本来源、旧回执与旧介质保管状态作为独立证据，绝不生成新版本回执；内容等同不被当作保管链等同。证据范围含新版本回执、旧版封验结论、旧回执、来源字节复验与旧介质保管链。

候选按新清单的文件路径、半开区间、长度、摘要联合查找。旧块即使摘要相同，若来源字节已变（`source_bytes_changed`）、旧版封验不可发布（`old_seal_not_publishable`）、来源介质在交接后隔离（`medium_quarantined`）、属于另一收件范围（`recipient_scope_mismatch`）或旧版没有冻结收件范围（`old_scope_unknown`），都不得进入可发布证明。

`reuse_plan` 是只读 dry-run：不写台账、不改写旧 manifest、回执与原始块文件；`freeze_plan` 才把新旧 manifest 版本、候选回执与介质链证据冻结进 `reuse_plan`，计划内容由其 `plan_id` 摘要固化，保管或来源变化会使重算计划得到不同 `plan_id`，组装时以 `plan_stale` 拒绝陈旧冻结。`assemble` 携带冻结计划时先对每个被选来源重新验字节，新版本块写 `receipt` 类组装证明，借用块写 `reuse_proof` 与 `reuse` 类组装证明（`assembled_proof` 统一记录每块位置与证明类型）。`seal` 区分本版本回执与有来源链的复用证明，复用证明在封验时再次复核来源字节与介质保管状态，缺一块或任一证明失效即为证据不足。

介质保管变化驱动可复用候选集合、组装与封验结论：隔离后的介质不再产生候选，组装后隔离会使已可发布版本重新封验为证据不足。`rollout.evaluate` 只在对应版本当前封验仍可发布时按收件验收推进波次，不沿用复用前的旧可发布结论。新版本普通 `receive`/`reconcile` 流程与复用计划并存且互不改写。
